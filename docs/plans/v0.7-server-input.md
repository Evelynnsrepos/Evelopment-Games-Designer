# v0.7 server: input for the server design

What the server design needs to know from Evelynn's roadmap, the app as of 0.6.0, and the server repo.

## The roadmap (Evelynn's words, summarized)

- A server application in its own GitHub repo, "Evelopment Games Designer Server".
- Easy to run for anyone on their own computer, or behind nginx (or similar) for a whole company.
- **No accounts.** After connecting to the server you get a **server-generated key** that grants permissions:
  **view** or **write**. You also enter a **name** when you access it. Both can be entered directly in
  Evelopment Games Designer.
- An **easy interface for non-technical users** (a web page or similar to run and manage the server).
- Requirement added on 2026-10-03: it must comply with **German law and security standards**.

## How the app works together today (0.6.0), and where a server plugs in

- **Data model:** each project is a folder of JSON files plus `assets/`. When shared, the project's state
  lives in one **Yjs document** (`collab/state.bin`), synced with y-protocols; edits merge without conflicts.
- **Network:** peer to peer with **iroh** (QUIC, end-to-end encrypted, NAT traversal, public relays as
  fallback). No server and no accounts. Each device has a key pair; its public key is the device id.
- **Transport interface:** `src/core/collab/transport.ts` (`CollabTransport`: `start`, `address`,
  `connect`, `send`, `disconnect`, `stop`). It was written so a **server transport can be added** next to
  iroh without touching the sync, undo or UI code.
- **Protocol:** `src/core/collab/protocol.ts`, version 1. A handshake checks protocol and schema version,
  project id, membership and an invite proof (HMAC over a secret in the invite code). Then Yjs sync,
  presence (awareness), chunked asset transfer (images and audio, 512 KB chunks, 200 MB per file),
  and since 0.6.0 a goodbye message (host closed / member left).
- **Roles (0.6.0):** the person who shares is the **host**. Only the host can remove people; when the host
  closes the project, everyone else is disconnected and asked whether to keep a local copy.
- **Not synced:** Sketch drawings (local only), each person's panel layout.

## Questions the design should answer

1. **Server's role:** an always-on peer that stores projects and relays between members (simplest:
   another Yjs participant using the same protocol), or a central store everyone syncs with?
2. **Keys:** how the server generates, shows, revokes and expires view/write keys, and how a key maps to
   permissions per project or per server. A read-only key must be enforced on the server
   (reject Yjs updates and asset uploads), not only in the app.
3. **Names without accounts:** names are self-chosen and unverified. Keep it that way, and say so in the UI.
4. **Transport:** WebSocket over TLS (works behind nginx and corporate proxies) vs. QUIC. TLS is needed
   either way for German/EU expectations (BSI TR-02102 recommendations).
5. **German law (GDPR/DSGVO, TTDSG/TDDDG):** which personal data is stored (names, IPs in logs, project
   contents), retention and deletion, a data processing agreement template for companies running it for
   staff, logging defaults (minimal, no IPs or IPs shortened), and an Impressum/Datenschutz page if run publicly.
6. **Admin interface:** a local web page (bound to localhost by default) to create projects, make and
   revoke keys, see who is connected, and back up or restore. A one-file installer or Docker image.
7. **Compatibility:** server and apps must share the protocol version; old apps are refused with a clear
   "please update" message (already supported by the handshake).
