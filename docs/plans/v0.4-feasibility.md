## Decisions (Evelynn, 2026-10-02)

- **Plugins:** no sandbox. On install, show a strong warning that the plugin gets full access and may affect P2P work in unexpected ways.

- **LLM:** it's part of v0.4. The model is downloaded separately from a button in the app settings. Dictionary spell check works without it.

## 1. Shift-click / replace tools

- **Where:** `src/shell/editor/Sidebar.tsx` (row `onClick`, lines 53 and 71) and `openComponent` in `src/shell/editor/actions.ts`.
  Today every click *adds* a panel (or focuses it if open). Shift-click = today's behaviour; plain click = new "replace layout with this tool".
- **Enter to confirm already works:** `confirmDialog` autofocuses the confirm button (`src/shared/ui.tsx:51`), so Enter presses it.
- **Saving first:** `closePanel` already flushes (`flushAll`) before closing; the replace path must do the same once for the whole layout.
- **P2P:** no conflict. The P2P branch keeps `layout` personal per computer (`PERSONAL_META_KEYS`), so replacing tools never affects teammates.
- **v0.3:** the v0.3 right-click menu lives on the same sidebar rows. Build this after v0.3 merges to avoid a conflict in `Sidebar.tsx`.
- **Open questions:**
  - Plain click on a tool that is already open: just focus it (today), or close everything else?
  - Plain click when exactly one *other* tool is open: replace silently (as the note reads), right?
  - This changes the default click everyone is used to. Keep drag-and-drop from the sidebar as is?

## 2. Spell check (German + English)

- **Nothing exists today.** Only the browser's built-in `spellCheck` attribute on the canvas text editor.
- **Don't rely on the built-in webview spell check:** Windows (WebView2) uses the OS language settings, macOS its own, and Linux (WebKitGTK)
  often none. No control over languages and no way to build our own suggestion UI on it.
- **Recommended:** the Rust crate `spellbook` (Hunspell-compatible, used by the Helix editor, MPL-2.0) behind a Tauri command, plus
  Hunspell dictionaries shipped with the app. It handles German compound words properly; the JS option `nspell` is known to struggle
  with German compounds and is slow to load the German dictionary.
- **Dictionaries / licence:** `en_US`/`en_GB` (SCOWL, permissive) and `de_DE` (igerman98, GPL-2.0/GPL-3.0 dual) are both fine for a
  GPL-3.0 app. More languages: LibreOffice's dictionaries cover ~100, mostly GPL/LGPL/MPL; download on demand instead of bundling
  (German alone is several MB). Licence of each extra dictionary needs a check.
- **Where it can show up:** rich text (TipTap: underline + right-click suggestions via decorations) and the canvas text editor are
  straightforward. Plain one-line `<input>` fields (names, list cells) can't show squiggly underlines; they'd need a different hint
  (e.g. a small marker) or be left out.
- **Per-project or per-user language** setting, plus a "personal dictionary" for made-up fantasy names (otherwise every invented
  word is flagged, which matters a lot in a game-design tool).
- **P2P:** spell checking is local only, nothing synced. A shared custom dictionary would be an optional extra.

### 2b. Local LLM

- Possible (e.g. llama.cpp via a Rust binding, a 0.5-1.5B model), but it's a 300 MB - 1 GB download, slow on older CPUs, and a big build
  dependency across three OSes. **Recommendation:** ship the dictionary spell check in v0.4, keep the LLM as a later optional download.

## 3. Plugins

- **Today tools are fixed at build time:** `COMPONENT_TYPES` is a hard-coded list (`src/core/model/components.ts`) and manifests are found
  with `import.meta.glob` at compile time (`src/core/registry.ts`). Plugins need both to become open-ended, which touches a core type used
  across the app (`references.ts`, registry, project loading). v0.3 is adding `cosmos` to the same list, so do this after v0.3 merges.
- **Loading:** a plugin is a folder (`manifest.json` + one built JS file) in the app data folder, loaded with a dynamic `import()`.
  Plugins must use the app's own React (expose it to them instead of bundling their own) and get a small, documented API
  (`useDocument`, entities, dialogs, theme variables).
- **Big risk, security:** plugin code runs inside the app with the same rights. Today the fs scope is `**` (whole disk,
  `src-tauri/capabilities/default.json`), so a malicious plugin could read or delete any file. Options: (a) warn clearly on install and
  only install what you trust (simple), (b) run plugins in a sandboxed iframe that talks to the app through messages (safer, more work).
  Recommend (b) for anything installed from other people's GitHub, or at least (a) plus narrowing the fs scope.
- **P2P:** plugin documents are plain JSON, so they sync like any tool. But a teammate without the plugin sees data with no tool to open it.
  Needs a rule: show "needs plugin X" and offer to install, and keep the data untouched.
- **Versioning:** the plugin API needs its own version number so old plugins don't break silently after an app update.
- **Docs + example repo:** easy once the API exists. Creating the new GitHub repo is something you'd approve (it's public).

### 3b. Plugin "store"

- Paste a GitHub repo URL, download its latest release zip, unpack into the plugins folder.
- Needs: an HTTP client (add `tauri-plugin-http` or do it in Rust; GitHub's download URLs don't allow plain browser `fetch`), a zip library
  (same as item 4), and zip-slip protection (no `../` paths when unpacking).
- Updates and uninstall should come with it. Same security catch as above, and GitHub's anonymous API limit is 60 requests/hour per user.

## 4. Export as zip

- Project folder layout is clean (`project.json`, `entities/`, `components/`, `assets/`; see `src/core/project/paths.ts`).
- Needs a zip library: `fflate` (small, MIT, JS) or the Rust `zip` crate. Rust is better for big asset folders (no loading everything into memory).
- "Downloads, but ask first": the native save dialog opened at `downloadDir()` (already available in `@tauri-apps/api/path`) does exactly that.
  `saveTextFile` in `src/core/export/` is the pattern to follow.
- **Leave out:** `.backups/` (can be huge) and, with P2P, the `collab/` folder (sharing keys and member list). Flush unsaved changes first.

### 4b. Import

- Unpack into the projects folder under a new name if one exists, then open it. Old exports get upgraded by the existing
  `schemaVersion` migrations (`src/core/project/versioned.ts`).
- **Must:** reject `../` paths (zip-slip), reject zips without `project.json`, size limit.
- **P2P:** an imported copy of a shared project must get a fresh project id and no share/member data, otherwise it would try to join
  the original group.
- **Open question:** importing a project that is newer than the app (made in a later version)? Recommend refusing with a clear message.

## Suggested order

1 (shift-click) and 4 (export/import) first; both are small and independent. Then 2 (spell check). Plugins last, since they need
v0.3 merged and the security decision made first.
